## 3. 事件契约（GF2-6）

```dart
enum GuardianAction { none, scheduled, gaveUp }

sealed class InstanceEvent {
  InstanceEvent(this.instanceId) : at = DateTime.now();
  final String instanceId;   // InstanceConfig.id
  final DateTime at;         // 事件发生时刻
}

final class InstanceStatusChanged extends InstanceEvent {
  final InstanceStatus from, to;
  final int? pid;   // running 时有值；首启 starting 为 null（进程未拉起），守护重启的 starting 有值
  final int? port;  // 实际监听端口（含 port==0 自动分配结果）
}

final class InstanceHeartbeat extends InstanceEvent {
  final bool ok;
  final int? latencyMs;  // ok=true 时为 TCP+HTTP 往返耗时
  final String? reason;  // ok=false 时的失败原因（tcp/http/status:xxx）
}

final class InstanceExited extends InstanceEvent {
  final int? exitCode;
  final GuardianAction action; // none=主动 stop；scheduled=守护将重启；gaveUp=转 crashed
}
```

发射规则：
1. `InstanceStatusChanged` 覆盖**全部**六态迁移（含 created→starting）；
2. `InstanceExited` 在**每次**进程退出时发射一次（主动停止 `action: none`）；
3. 同一次异常退出的发射顺序固定：`Exited` → `StatusChanged`（先事实、后守护决策结果）；
4. 日志行**不进**事件流（Gate-A §4.6 防洪泛）；UI 取日志走 `LogTail.tail` 轮询或文件 watch；
5. 事件流为 `StreamController.broadcast()`，无背压承诺（UI 侧自行消化）。

## 4. InstanceSupervisor 详细设计

### 4.1 常量与新增字段

```dart
// Guardian 参数（BQ1：全局常量）
static const _gInitial = Duration(seconds: 1);
static const _gFactor = 2;
static const _gMaxDelay = Duration(seconds: 30);
static const _gMaxFailures = 3;

Timer? _restartTimer;            // 守护重启定时器
int _failures = 0;               // 连续失败计数（running 重启成功即清零）
final StreamController<InstanceEvent> _events; // broadcast
HealthProbe? _probe;             // running 期间存在
LogTail? _logTail;               // start 时创建，随实例存活
```

### 4.2 状态迁移表（权威）

| # | 当前态 | 触发 | 动作 | 次态 | 事件 |
|---|---|---|---|---|---|
| T1 | created/stopped/crashed | `start()` | `_failures=0`；解析端口；`_launch`；`_awaitReady` | starting → running | StatusChanged(→starting)；StatusChanged(→running) |
| T2 | running | 进程退出（exit 回调，非 stopping） | `_failures+1`；`<3` → 调度退避重启；`==3` → 停守护 | starting（守护中）/ crashed | Exited(scheduled/gaveUp) → StatusChanged |
| T3 | starting（守护等待中） | `_launch`/`_awaitReady` 失败 | 先 `kill` 残留进程；`_failures+1`；同 T2 分支 | starting / crashed | —（由后续退出/重试路径补发） |
| T4 | starting（定时器挂起） | `stop()` | 取消 `_restartTimer` | stopping → stopped | StatusChanged；Exited(none) 视残留而定 |
| T5 | running | `stop()` | probe.detach；置 stopping；优雅终止（10s 超时→sigkill） | stopping → stopped | StatusChanged；Exited(none) |
| T6 | running/starting | `restart()` | 等价 `stop()`（抑制守护）→ `start()`（内部清零计数） | stopping → starting → running | 复用 T5/T1 事件 |
| T7 | starting（守护中） | 心跳连续 3 败回调 `onZombie` | kill 进程 → 走 T2/T3 路径 | starting / crashed | Heartbeat(fail)×3 → 同 T2 |
| T8 | crashed | `start()` | 同 T1（复位语义） | starting → running | 同 T1 |

关键澄清：
- **`_awaitReady` 超时但进程仍存活**（T3 特例）：视为失败，先 kill 再计数，防孤儿进程；
- **初始 `start()` 失败仍会抛出**（保持既有契约，`selfcheck_manager` 兼容），但若进程曾成功拉起后退出，守护已在后台接手——调用方应以事件流为权威状态源；
- N5 口径：**「重新 spawn」动作 ≤5s**（首次 1s 即发起）；达到 `running` 的总时长受 dsh 自身启动耗时影响，不受 N5 约束。

### 4.3 守护流程（伪代码）

```
onProcessExit(code):
  if state.status == stopping:            # T5
    status = stopped; emit Exited(none); emit StatusChanged; cleanup; return
  _probe?.detach()
  _failures += 1
  if _failures >= _gMaxFailures:          # gave up
    status = crashed; emit Exited(gaveUp); emit StatusChanged(→crashed); return
  emit Exited(scheduled)
  status = starting; state.guardianAttempts = _failures; emit StatusChanged(→starting)
  _restartTimer = Timer(_delay(_failures), _guardianRestart)

_guardianRestart():
  if state.status in {stopping, stopped}: return
  try:
    port = _resolvePort(cfg)              # port==0 → 重新取空闲端口（结果写回 state.port）
    proc = _launch(cfg, port)             # 抽取自现 start()（supervisor.dart:40-48）
    await _awaitReady(cfg, port)
    _failures = 0; state.guardianAttempts = 0
    status = running; emit StatusChanged(→running); _probe.attach(port)
  catch:
    proc?.kill(); → 走 T3 分支（计数 + 下一轮/crashed）

_delay(attempt) = min(_gInitial * _gFactor^(attempt-1), _gMaxDelay)
```

## 5. HealthProbe 详细设计（GF2-2）

```dart
class HealthProbe {
  HealthProbe({
    required this.onHeartbeat,   // void Function(bool ok, int? latencyMs, String? reason)
    required this.onZombie,      // void Function() —— 连续失败阈值触发
    this.interval = const Duration(seconds: 3),
    this.failureThreshold = 3,   // BQ2
    this.tcpTimeout = const Duration(milliseconds: 800),
    this.httpTimeout = const Duration(seconds: 2),
  });
  void attach({required String instanceId, required String host, required int port});
  void detach();
  Future<({bool ok, int? latencyMs, String? reason})> pingOnce();
}
```

探测流程（单次 `pingOnce`）：
1. `Socket.connect(host, port, timeout: tcpTimeout)` → 成功即销毁（快速区分「端口死了」与「HTTP 层异常」）；
2. `HttpClient` GET `http://host:port/`（`connectionTimeout: httpTimeout`，`maxRedirects: 0`）；
3. 状态码 200–499 判 ok（沿用 `_awaitReady` 判据，`supervisor.dart:121`）；durables 记 latency。

运行规则：
- 周期定时器 3s；**防重入**：上一轮未完成则跳过本轮（`_checking` 标志）；
- ok → `_fails=0`，发 `Heartbeat(ok, latencyMs)`，并更新 `InstanceState.lastHeartbeat`；
- fail → `_fails+1`，发 `Heartbeat(false, reason)`；连续 `≥3`（≈9s）→ `_fails=0`、`detach()`、回调 `onZombie()`（由 Supervisor 杀进程 → 走 §4.3 守护路径）；
- `detach()` 取消定时器并复位计数；`stopping/stopped` 必须处于 detach 态（RF2-1 竞态屏蔽）。

## 6. LogTail 详细设计（GF2-4）

```dart
class LogTail {
  LogTail({this.capacity = 2000, required this.logFile, required this.sink});
  void handleChunk(String chunk, {required bool stderr});
  List<String> tail(int lines);
  String export([String? path]);
}
```

要点：
1. **行缓冲**：进程输出按 chunk 到达可能切断行；内部 `_pending` 缓冲，遇 `\n` 才成行（避免环形缓冲出现半行）；
2. **双写**：成行后同时写入环形缓冲（`ListQueue.addLast`，超容量 `removeFirst`）与文件——文件为完整日志（追加写，跨重启保留）。**实现注记**：文件写采用同步 `RandomAccessFile`（追加模式）——实测 `IOSink.flush()` 在退出回调与 dispose 交错场景会抛 `StreamSink is bound to a stream`；
3. **时间戳前缀**：`yyyy-MM-dd HH:mm:ss.SSS`；stderr 行追加标记 `[stderr] `（便于区分流来源）；
4. `tail(lines)`：取环形缓冲最后 N 行（快照副本）；
5. `export([path])`：`path==null` 返回原文件路径；否则复制文件到 path 并返回新路径；
6. 容量 2000 行（BQ4）；内存占用 ≈ 2000 × 行长，忽略不计。

## 7. RegistryStore 增强与 InstanceManager（GF2-5）

### 7.1 RegistryStore 新增 API（`registry.dart`）

```dart
void upsert(InstanceConfig cfg);   // 按 id 替换，不存在则追加；立即 save

```
- `schemaVersion` 保持 1（字段无迁移）；每次变更即落盘（与现 `save` 一致）。

### 7.2 InstanceManager（新门面，`instance_manager.dart`）

现有 `InstanceSupervisor` 为**单实例**语义（一个对象一组 `_process/_state`，`supervisor.dart:15-16`）。为支撑多实例与 F2.1，新增薄门面（组合，不重写守护逻辑）：

```dart
class InstanceManager {
  InstanceManager({required this.env, required this.registry});
  Stream<InstanceEvent> get events;                    // 聚合各 supervisor 事件（内部转发）
  Future<InstanceState> create(InstanceConfig cfg);    // registry.upsert + start
  Future<InstanceState> start(String id);
  Future<int?> stop(String id);
  Future<InstanceState> restart(String id);
  Future<void> remove(String id);                      // stop(若在跑) + registry.remove + supervisor.dispose
  InstanceState? stateOf(String id);
  LogTail? logTailOf(String id);
  List<InstanceConfig> list();                         // registry.load()
  Future<List<InstanceState>> startAutoStart();        // autoStart==true 逐个 start；单实例失败不阻断
}
```
- 事件聚合：create 时订阅 supervisor.events 转发到聚合流；remove 时取消订阅并 dispose；
- `startAutoStart` 失败隔离：单个实例失败记入返回值外的事件流，不中断其余实例。

## 8. 关键时序

### 8.1 崩溃自动拉起（T2 主路径）
```
running --dsh 异常退出--> [Exited(scheduled)] --> StatusChanged(running→starting)
   --1s--> _guardianRestart --成功--> [StatusChanged(→running)] + Heartbeat 恢复
                          --失败--> 计数+1 --2s--> ...（≥3 次 → crashed）
```

### 8.2 僵死自愈（探针触发）
```
running --心跳 fail×3(≈9s)--> onZombie --> kill 进程 --> exit 回调 --> 同 8.1
```

### 8.3 restart
```
running --restart()--> stop(10s 内 graceful / sigkill, 抑制守护) --> stopped
       --> start(清零计数) --> starting --> running
```

## 9. 自检设计 `tool/selfcheck_lifecycle.dart`

真机自检（沿用 selfcheck 系列风格，PASS/FAIL + ALL PASS 退出码）。用例：

| # | 用例 | 步骤 | 断言 |
|---|---|---|---|
| C1 | 正常起停回归 | start→running→stop | 同 selfcheck_manager 既有断言（兼容性） |
| C2 | 崩溃拉起（N5） | running 后 `Process.run('taskkill', ['/F','/PID',pid])` 强杀 | 收到 `Exited(scheduled)`；**≤5s 内观测到新一轮 spawn**（以 Exited→下一次 StatusChanged(→running 前的 starting) 时间差计）；最终 running |
| C3 | 连续失败→crashed | 用临时 `process.exit(1)` 脚本构造 `NodeEnv.forDshCli(node, fake.js)` 的独立 supervisor，start（预期抛出） | 轮询 ≤60s 内 status==crashed；事件含 `Exited(gaveUp)` |
| C4 | crashed 复位 | C3 后对同一 supervisor `start()` | 抛出后继续轮询（守护仍会按 starting 重试语义）或换真实 env 的 supervisor start 成功 running |
| C5 | restart | running 后 `restart()` | 事件序列含 stopping→starting→running；最终 running |
| C6 | 心跳与自愈 | running 后 `probe.pingOnce()` ok==true；再以 `attach` 指向空端口验证 fail 事件 | Heartbeat(ok/latency) 与 fail(reason) 均可达 |
| C7 | Registry CRUD + autoStart | 临时文件 upsert/remove/get 往返；autoStart=true 配置经 `InstanceManager.startAutoStart()` | 回读一致；autoStart 实例 running |
| C8 | dispose 无泄漏 | remove 实例后再 stop/start | 不抛异常，事件流已关闭（订阅收不到新事件） |

> 预计耗时 2–4 分钟（含 dsh 真实起停 2–3 轮）。C3 的 fake 脚本写入系统临时目录，用后删除。
