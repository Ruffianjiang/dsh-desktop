## 1. 背景与动机

1.1. 现状：v0.1.0–v0.3.0（Electron → Tauri 2）均为「桌面壳 + 内嵌 dsh web 界面」，本质是套一层窗口加载 dsh 自带的网页应用。

1.2. 问题：
1. UI、交互、品牌完全受限于 dsh web 前端，无法做自定义多端体验；
2. 对 dsh 引擎本身无管理能力（安装/升级/多实例/生命周期均由用户手工操作）；
3. 「壳」与「被包页面」耦合，违背高质量原生桌面应用目标。

1.3. 新方向（本文档目标）：构建 **dsh 管理平台**：
1. 管理 dsh 引擎：安装、升级、启动、停止、多实例守护；
2. **自研跨平台原生对话 UI**（不加载、不嵌入 dsh web 页面）；
3. UI 通过 **dsh 自身结构化 API（REST + SSE）**直连，实现真实原生客户端；
4. 目标平台矩阵：**Windows / macOS / Linux（Flutter 主客户端）+ 鸿蒙 NEXT 桌面（ArkTS/ArkUI 独立客户端）**。

1.4. 事实基础（2026-09-03 本机 bundle 源码实测，见 §9 附录）：
1. dsh 是 Cordis 插件框架的 profile 启动器，`web` profile = `dsh-base` + `dsh-web-app`；
2. dsh 服务端暴露与 SPA 解耦的 `/api/*`（REST 上行 + SSE 下行），可被任意语言客户端直连；
3. `/api/*` 由 `dsh-host-apiproxy` 注册，HTTP/upgrade 由 `dsh-host-webserver` 提供（host 默认 `127.0.0.1`，端口可配），二者与浏览器层解耦。

1.5. 鸿蒙桌面端决策纪要（2026-09-03，用户确认）：
1. 平台范围扩展为**四端**：Windows / macOS / Linux + **鸿蒙桌面端**（HarmonyOS NEXT PC）。
2. 鸿蒙端定位（用户最新决策 2026-09-03）= **ArkTS/ArkUI 独立客户端 + 本地引擎管理诉求**：对话工作台 + 在鸿蒙设备上安装/启动/停止 dsh；后者受鸿蒙 NEXT 应用沙箱能力约束，可行性列为 **P0 预研（R6/M1.5）**——通过则应用内托管；未证实则回退为「客户端 + 管理远端/托管实例」（D8 端点模型保留，见 D6）。
3. 鸿蒙端 UI = **ArkTS/ArkUI 原生**第二码库；与 Flutter 码库共享**语言中立的 L3 协议契约**（Dart/ArkTS 双实现 + 契约测试对齐）。
4. 事实背景：鸿蒙桌面开发栈为 DevEco Studio + ArkTS/ArkUI（Stage 模型，HAP 上架）；Flutter 官方未支持鸿蒙（Flutter-OH 为社区/华为适配，桌面成熟度存疑）；鸿蒙 PC 用户态为 musl/OpenHarmony ABI（Node 需 ohos 专用构建）。
5. 发版范围修正（v1.1）：鸿蒙端**立项**先行，不纳入本次发版；开发与 M1.5 预研延后至其他机器进行，不阻塞主客户端 M1–M4。

## 2. 目标与非目标

2.1. 目标（v0.4.0 系列）：
- G1 引擎管理：安装/升级/卸载 dsh，探测并校验 Node 运行时，管理 DSH_HOME 与 profile。
- G2 实例生命周期：创建/启动/停止/重启 dsh 后台服务实例，健康检查、崩溃自动拉起、日志可视化。
- G3 原生对话 UI：自研 Flutter Desktop 客户端，多会话、流式输出、工具调用与审批、附件。
- G4 API 直连：实现 dsh 协议客户端（REST unary RPC + SSE 事件流），不依赖 dsh web 前端。
- G5 发布：Windows / macOS / Linux 桌面（Flutter）三端打包与自动更新；鸿蒙桌面端 HAP 打包与上架（M5）。
- G6 鸿蒙桌面端（ArkTS）：对话工作台 + 本地引擎管理——本地安装/启停/守护 dsh 以 R6/M1.5 预研结论为准；预研不通过则仅连接远端/托管实例（F6）。

2.2. 非目标（首版明确不做）：
- N1 对远程/多机 dsh 实例做**托管式管理**（在远端安装/升级/启停 dsh）不做；但客户端可**连接**任意 dsh 服务端点（含远端）——鸿蒙客户端形态依赖此能力；
- N2 移动端 / Web 端（鸿蒙手机不在首期）；
- N3 dsh 插件生态的图形化「完整」管理（仅基础浏览与启停）；
- N4 多人协作 / 账号体系（本地单用户 + 远端端点凭据）；
- N5（待预研）鸿蒙端本地引擎托管不作默认承诺：是否可在鸿蒙设备本地 spawn/常驻 Node/dsh 由 P0 预研（R6/M1.5）判定；默认路径优先「客户端 + 远端/托管实例管理」，本地托管仅在预研通过后纳入。引擎托管确定平台为 Win/macOS/Linux。

## 3. 术语

| 术语 | 定义 |
|---|---|
| dsh | DeepSeek Harness CLI（Node.js，Cordis 插件框架），本平台管理的目标引擎 |
| profile | `$DSH_HOME/profiles/<name>` 下的 bundle 组合，`dsh --profile <name>` 启动 |
| bundle | `@deepseek-ai/dsh-*` 的 Cordis 插件包，可组合出不同 profile |
| 实例（Instance） | 本平台创建并守护的一个 dsh 后台服务（含所属 profile、端口、数据目录、日志） |
| 端点（Endpoint） | 一个可连接的 dsh API 服务地址（host:port + 协议）；可为本机托管实例或远端 dsh 服务（D8） |
| SSE | Server-Sent Events，dsh 下行事件流通道（`/api/events.mux|host`） |
| 信封（Envelope） | SSE/RPC 帧的传输封装（ServerRequest 结构 + 类型化载荷） |

## 4. 总体架构

```
┌──────────────────────────  dsh 管理平台（Flutter Desktop，纯 Dart）  ──────────────────────────┐
│  L1 UI 层       会话工作台 / 引擎管理面板 / 设置（自研组件，无 dsh web 页面）                    │
│  L2 管理层      引擎管理（安装/升级） · 实例生命周期（启停/健康/守护/日志） · 配置               │
│  L3 连接层      dsh API Client：REST unary RPC + SSE 事件流 + 信封编解码 + 重连                 │
└───────────────┬──────────────────────────────────────────────┬─────────────────────────────────┘
                │ 进程管理（spawn/stop/signal）                  │ HTTP + SSE（127.0.0.1:<port>）
        ┌───────▼────────┐                                ┌─────▼──────────────────────────┐
        │ dsh 守护进程     │                                │ dsh 服务端（首版 web profile）   │
        │ （Node 进程）     │                                │ /api/rpc · /api/events.* · ...  │
        └─────────────────┘                                └────────────────────────────────┘
```

4.1. 架构决策要点：
1. **Win/macOS/Linux = Flutter 码库（纯 Dart）**：UI、进程管理、API 客户端全部 Dart 实现（`dart:io Process` 负责 spawn/守护，HTTP/SSE 用 `http` + `dart:convert`/`Stream` 实现）；**不引入 Rust/FFI 桥**。旧 Rust/Tauri 骨架仅保留为历史 tag/legacy，不参与新架构。（见 D1/D4）
2. **鸿蒙桌面端 = ArkTS/ArkUI 原生码库（独立客户端：对话 + 引擎管理诉求）**：UI 与业务逻辑在 ArkTS 实现，L3 协议按语言中立契约复刻（D7）；本地引擎托管是否可行由 P0 预研判定（D6/M1.5）。
3. **首版服务形态 = web profile 守护进程**：本平台作为其 API 消费者，从不加载其前端页面；纯 API profile 为 M2+ 优化项（见 §8，D2）。
4. **客户端面向「服务端点」（Endpoint）**：端点 = 本机托管实例 或 远端 dsh 服务；「引擎托管能力」与「客户端连接」解耦，同一 L3 客户端两态复用（见 D8）。
5. UI 与 dsh 之间**唯一通道是 L3 API 客户端**，保证「非外壳」架构约束不因迭代而回退。

## 5. 技术选型与决策记录（ADR）

| 编号 | 决策 | 结论 | 理由 | 备选与代价 |
|---|---|---|---|---|
| D1 | Win/macOS/Linux UI | **Flutter Desktop** | Skia 自绘非 WebView；聊天类 UI 生态成熟；AOT 高性能、三端一致；满足「高性能+高质量」 | Tauri2 自研（渲染仍 WebView）；Rust egui/iced/Slint（对话级 UI 成本过高） |
| D2 | dsh 服务形态 | 首版 **web profile 守护**；纯 API profile 列入优化 | /api/* 与 A 同实现、时延一致；web profile 官方零组合风险 | 纯 API profile 更省内存，但 bundle 组合未官方保证，需实测（风险后置） |
| D3 | 代码与发布 | 复用 **dsh-desktop** 仓库，v0.4.0 起 | 延续 tag/Release/自动更新基建；electron 与 tauri-skeleton 标 legacy | 新仓库需重建基建 |
| D4 | 客户端语言 | **纯 Dart**（不引 Rust FFI） | 单语言栈；Process/HTTP/SSE 在 Dart 桌面可用且足够；避免桥接复杂度 | Rust 管理层性能略优但引入 FFI/线程模型复杂度 |
| D5 | 连接协议 | dsh 原生 **REST + SSE**（`/api/rpc`、`/api/events.*`） | 官方客户端同类实现（`dsh-client-connection`）可作蓝本；不依赖其 web 前端 | Typert 网关（`dsh-api-gateway`）更深集成留远期 |
| D6 | 鸿蒙桌面端定位 | **独立客户端 + 本地引擎管理（诉求）**；本地托管可行性 P0 预研，不通过则回退客户端 + 远端托管 | 用户决策 2026-09-03；本地托管受鸿蒙 NEXT 沙箱约束未证实，前置 M1.5 实测 | 纯客户端形态（预研不通过即回退此态，D8 端点模型不变） |
| D7 | 鸿蒙端 UI | **ArkTS/ArkUI 原生**（第二码库） | 一等公民、桌面适配成熟、体验与维护最优；与 Flutter 端共享 L3 契约 | Flutter-OH 同码库（非官方平台、桌面成熟度存疑） |
| D8 | 连接模型 | 客户端面向**服务端点**，托管与连接解耦 | 同一 L3 客户端连本机实例与远端 dsh；鸿蒙端复用端点语义 | 仅本机 127.0.0.1（无法支撑鸿蒙客户端形态） |

## 6. 功能拆解（编号贯穿，供排期与验收引用）

### F1 引擎管理
- F1.1 环境探测：检测 Node（版本满足 dsh 要求）、`dsh` CLI、`DSH_HOME`/npm 全局目录（可写性）。
- F1.2 安装 dsh：以指定版本 `npm i -g dsh@<ver>` 安装；展示进度/错误；幂等。
- F1.3 升级 / 回滚：列出已发布版本（registry 查询），执行升级/回滚，保留版本记录。
- F1.4 Profile 浏览：读取 `$DSH_HOME/profiles` 与 bundle 构成，只读展示（F1 期）。
- F1.5 卸载（谨慎路径，二次确认）：移除 npm 全局包，保留 DSH_HOME 数据。

### F2 实例生命周期
- F2.1 创建实例：选择 profile（默认 web）、端口、数据目录、别名；写实例配置。
- F2.2 启停控制：start/stop/restart；start 采用无窗口后台 Node 进程（Windows 下隐藏控制台窗口）。
- F2.3 健康检查与守护：TCP/HTTP 就绪探针（GET 就绪端点或端口探测）+ 心跳；异常退出自动拉起（带退避与上限）；退出码与 stderr 落日志。
- F2.4 日志：按实例采集 stdout/stderr，环形缓冲 + 落盘；UI 内实时查看与导出。
- F2.5 实例状态面板：运行/停止/崩溃/启动中；端口、PID、内存、启动时长。

### F3 dsh API 客户端（连接层）
- F3.1 上行 RPC：`POST /api/rpc`（unary）调用（如建会话、发消息、资源 CRUD）。
- F3.2 下行事件流：SSE 订阅 `/api/events.mux`（会话/agent 事件）与 `/api/events.host`（host 事件）；`\n\n` 帧解析 + 信封校验。
- F3.3 资源端点封装：sessions / session-search / llm / skills / subagents / goals / credentials / approvals / respond / workspace 的类型化封装。
- F3.4 可靠性：断线重连（指数退避）、心跳/游标去重、单流背压控制。
- F3.5 类型映射：以 zod schema 为源生成类型（Dart/ArkTS，工具链见 R3）。
- F3.6 端点寻址与连接管理：端点 = host:port（本机实例自动发现 / 远端手动配置）；连接状态机（连接/重连/鉴权/健康）。

### F4 对话工作台
- F4.1 会话管理：会话列表、新建、删除、归档、搜索、切换。
- F4.2 对话与流式输出：发送消息 → RPC 上行 → SSE 流式渲染（markdown、代码块高亮、内联表格）。
- F4.3 工具调用与审批：展示工具执行轨迹（名称/参数/结果/耗时）；需要审批的工具（ask-user/approvals）在 UI 内审批。
- F4.4 子代理与技能：会话内 subagent 展开、技能（skill）触发状态展示。
- F4.5 附件：文件引用/附件上传（映射 dsh attachment 域）。

### F5 系统集成
- F5.1 系统托盘：最小化到托盘、托盘菜单（打开/全部停止/退出）。
- F5.2 开机自启：注册/注销系统自启（dsh 服务实例与/或本应用）。
- F5.3 设置：实例默认端口、数据目录、主题、模型选择入口（读写 `/api/settings`）。

### F6 鸿蒙桌面端专项（ArkTS 码库）
- F6.1 端点/服务连接管理：本机托管实例或远端端点列表、连接状态与凭据（复用 D8 端点语义）。
- F6.2 本地引擎管理（以 R6/M1.5 为准）：安装/启停/守护 dsh 的最小集；预研不通过则该项转为「远端托管实例管理」。
- F6.3 对话工作台：交互与渲染规格复用 F4（ArkTS 独立实现）。
- F6.4 安全与合规：HAP 签名/上架前置、权限声明与鸿蒙沙箱适配。

## 7. 非功能需求（NFR）

| 编号 | 项 | 指标（目标） |
|---|---|---|
| N1 | UI 冷启动 | 首窗口 < 2s（Flutter release） |
| N2 | 消息首帧延迟 | 本地实例：发送后首个 token 到达显示 < 1s |
| N3 | 大会话渲染 | 千条消息会话可流畅滚动（虚拟化） |
| N4 | 内存占用 | UI 进程稳态 ≤ 300MB（不含 dsh 服务进程） |
| N5 | 崩溃恢复 | dsh 服务异常退出 ≤ 5s 自动拉起（退避上限内） |
| N6 | 安全 | dsh 服务默认绑定 127.0.0.1；token/凭据仅存系统凭据库或本地加密 |
| N7 | 升级一致性 | dsh 引擎升级不影响既有实例数据与配置 |
| N8 | 端点与远端安全 | 远端/局域网端点须显式配置并支持凭据；本机服务默认仍绑 127.0.0.1，暴露到局域网需显式开关 |
| N9 | 双端协议一致 | L3 契约（Dart/ArkTS 两实现）以契约测试对齐，杜绝两端漂移 |

## 10. 附录：侦察事实（2026-09-03 本机实测）

### 10.1 dsh 概况

### 10.2 API 端点清单（服务端 `dsh-host-apiproxy` 注册）
| 方向 | 端点 | 用途 |
|---|---|---|
| 上行 | `POST /api/rpc` | unary RPC（建会话/发消息等） |
| 上行 | `/api/respond` | 应答（ask-user 等） |
| 上行 | `/api/sessions` `/api/session-search` | 会话 CRUD / 检索 |
| 上行 | `/api/llm` `/api/models` | 模型层 |

### 10.3 传输细节
- 下行 SSE 采用 streaming fetch（非 EventSource），`\n\n` 帧 + ServerRequest 信封 + zod schema（MuxFrame/HostFrame，`discriminatedUnion('type')`）。
- 路由注册：`dsh-host-apiproxy`；HTTP 服务：`dsh-host-webserver`（host 默认 `127.0.0.1`，port 可配）；二者与 `dsh-web-app` 浏览器层解耦。
- 客户端参考实现：`@deepseek-ai/dsh-client-connection`（HTTP-up/SSE-down，ConnectionController 双流 + 重连 + fixture api）。
